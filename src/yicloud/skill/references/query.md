# 查询已有开发机和 Job

## 确定查询范围

查询清单或单项状态时读取。沿用用户指定的账号、项目和可用区；缺少时先看 `context show`，已有明确范围不重新配置账号。

- 缺项目或可用区时，按需执行 `project list --all`、`resources zones`。唯一且符合用户要求的候选可直接使用；多个候选只补问尚未确定的范围，不默认选第一项或扫描全部项目。不要从历史资源记录猜当前范围。
- “当前有哪些”默认查询已确定的项目、可用区，并在结果中说明覆盖范围；不是整个账号所有地域的清单。“所有人”改变个人筛选，不自动扩大项目和可用区。
- 明确要求所有项目或可用区时，先取得当前账号、地域下的真实项目和可用区清单，再分别查询要求覆盖的组合；不可访问的组合单列为未查明。只查一个可用区不能声称覆盖项目的全部可用区，也不能把当前地域说成所有地域。

## 查询清单

“我的”与“当前项目可见的”使用不同筛选：

| 目标 | 开发机 | Job |
|---|---|---|
| 我的资源 | `--set 'Creator="平台用户名"'` | `--set 'Self=true'` |
| 当前范围可见资源 | 不加个人筛选 | 不加个人筛选 |

查询个人开发机前，先核实 Creator 所需的平台用户名；不要用本地账号别名，也不要省略 Creator 试查。优先复用当前账号已确认的用户名；用户同时查询两类资源时，可先查个人 Job，复用本次 `Self=true` 结果中唯一且无身份矛盾的创建者（有 RealCreator 时需与 Creator 一致）。没有可靠身份依据时只补问用户名；已完成的 Job 查询仍可交付。仅查开发机时不额外遍历 Job。

以下使用已确认的 `project`、`zone`；`creator_filter` 是 `Creator=` 加平台用户名的 JSON 字符串，例如 `Creator="user@example.org"`，必须换成真实值。明确只查一种资源时仅执行对应命令：

```bash
yicloud --json workspace list --project "$project" --zone "$zone" --all --set "$creator_filter"
yicloud --json job list --project "$project" --zone "$zone" --all --set 'Self=true'
```

查询可见清单时移除上面的个人筛选。取得完整清单使用 `--all`，不要另写分页脚本；它遍历当前请求范围内的分页，不会遍历项目或可用区。未要求只看运行中时，保留已停止、失败或完成但仍在清单中的资源，不自行加状态过滤。

## 查询指定资源状态

已有真实 ID 时调用 `workspace status` 或 `job status`；仍须提供项目、可用区或从 context 补齐。按名称查询使用 `--by-name`，个人筛选相应改用 `--lookup-set`，如 Job 的 `--lookup-set 'Self=true'`。CLI 会在范围内完整分页并精确消歧，零匹配或重名不选择第一项，也不把列表的模糊名称过滤当作唯一定位。

列表已有状态就直接汇总，不逐项调用 status。缺少状态或需要核对某一项时再查详情；未知状态保留原值，不推断成功、停止或不存在。纯清单和状态查询不需要 SSH、日志、replicas、等待终态或创建资源。

## 交付与不完整结果

分别汇总开发机和 Job，给出名称、真实 ID、项目、可用区及实际状态，说明本次账号和查询范围。只输出这些查询所需信息，不展开启动命令、环境变量或无关任务内容。

- 使用正确的个人筛选并完整分页后，空结果报告为“该范围内未返回个人资源”，不扩张为平台上全局没有资源。已有未加个人筛选的列表不作为个人结果。
- 一类查询失败时仍交付另一类已查到的结果；权限错误、网络失败、未完成分页或缺少筛选信息属于未查明，不记作零条。
- 说明未查询的项目、可用区或未核验的个人归属；不为消除这些缺口擅自切换账号、修改 context 或创建资源。
