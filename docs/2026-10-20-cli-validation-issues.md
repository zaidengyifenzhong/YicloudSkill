# CLI 完善与真实任务验证问题记录（2026-10-20）

本文记录本轮命令完善、独立测试和最小 Job 真实联测中出现的问题。已修复、已绕过、尚未确认原因和未验证范围分别标记；本地 dry-run 或模拟测试通过不等于平台验证通过。真实账号、项目、资源 ID、每次请求和完整事件记录保存在 Git 忽略的本轮 `.local/` 证据目录，不在此发布凭据或用户研究任务内容。

## CLI-01：空接口描述导致 CLI 启动失败

- 状态：已修复，离线复测通过。
- 触发：为缺失入口生成命令时，有些 API 目录项的 description 是空字符串。
- 现象：访问 `description.splitlines()[0]` 抛出 IndexError，连 `--help` 也无法启动。
- 处理：描述为空时回退到 Action 名称。
- 验证：逐一检查 225 个 HTTP 操作对应的命令帮助；182 个新增命令通过字段参数及完整请求文件的 dry-run 测试。

## CLI-02：测试误把脱敏输出当成原始请求

- 状态：测试修正，脱敏行为保留。
- 触发：用同一个合成字符串同时填写 Password/AccessKey 和其他字段，再直接比较 dry-run 输出与未脱敏请求。
- 现象：已识别的秘密值在整个输出中被替换，导致断言失败；`--show-secrets` 也不会重新显示已知输入凭据。
- 处理：在客户端 dry-run 边界捕获实际请求参数，核对字段转换；另加独立断言验证秘密不出现在输出中。
- 结论：这里是测试预期错误，不能以放宽脱敏来让测试通过。

## CLI-03：文件目录分页不识别 Files 响应

- 状态：已修复，独立复测通过。
- 触发：`yicloud fs list-dir --path PATH --all`。
- 现象：官方接口返回 `Data.Files`，原列表提取器仅识别 Items 等字段，报 `Unrecognized list response`。
- 处理：列表提取器增加 Files 支持。
- 验证：独立模拟官方 Files/Limit/Offset/Total 结构的两页结果，确认完整聚合。
- 依据：[ListDir 官方文档](https://api.yicloud.com.cn/fs/list_dir.html)。此处为公开文档核对与离线回归，不能视作认证平台联测。

## CLI-04：服务端限制页大小时提前结束并漏数据

- 状态：已修复，独立复测通过。
- 触发：`volume list-quota-group-volumes --all --limit 200`；该接口文档规定每页最大 100。
- 复现：服务端共有 150 条，实际首批返回 100 条。原代码以“实际数量等于请求 Limit”作为继续条件，于是仅取一页并错误报告 100 条完成。
- 处理：存在有效 Total 时，按当前 Offset 加实际返回数量判断是否继续；Offset 按实际数量推进。未到 Total 就收到空页会明确报错，不将不完整结果报告为成功。
- 验证：覆盖服务端限制每页条数、非零初始 Offset、空列表及缺少 Total 的响应。
- 依据：[ListQuotaGroupVolumes 官方文档](https://api.yicloud.com.cn/volume/list_quota_group_volumes.html)。

## CLI-05：末页重复可能绕过重复页检测

- 状态：已修复，独立复测通过。
- 触发：服务端忽略 Offset，返回与上一页相同的数据，且重复合并后的条数恰好达到 Total。
- 现象：原流程先合并、再判断总数退出，可能在退出前没有检测这一重复页。
- 处理：每页合并之前检查页面内容指纹；重复页返回错误。
- 验证：独立覆盖“第二页重复且恰好达到 Total”的边界。

## LIVE-01：节点实时容量查询鉴权失败

- 操作：读取当前账号的项目、可用区和 CPU workload 配额组后，使用实时返回的 PoolId 查询可用节点。
- 结果：平台返回 code=101、`鉴权失败`。初次容量查询的资源池参数不作为最终证据；使用实时 PoolId 的复查仍返回同样错误。

## LIVE-02：CreateJob 策略参数本地校验通过但平台拒绝

- 状态：已找到可创建的请求组合；策略参数组的兼容性差异已复现，字段级单因仍未确认。
- 基础请求：单副本、1 CPU、1Gi 内存、GPU="0"，使用实时确认的 CPU 任务配额组与公共镜像，并尝试挂载本轮专属产物目录。
- 第 1 次：完整有界请求经 dry-run 通过，平台返回 code=1001000、`任务规格不合法`。
- 第 2 次：补充 Qos=Guaranteed、Priority="5" 后，仍返回同样错误，不能声称 QoS 是根因或已解决。
- 第 3 次：去掉 GPU、Internet、TaskSpec 级运行/等待时限及 RestartPolicy，改用测试进程内 alarm 限时，返回 code=100、`任务资源参数错误`。
- 第 4 次：恢复 GPU="0"，再次返回 code=1001000、`任务规格不合法`。
- 第 5 次：仅增加 UsePrivateMachine=true，仍返回 1001000。
- 第 6 次：仅将结构化挂载换为 TaskSpec.MountGPFS 字符串，仍返回 1001000。
- 第 7 次：增加 EphemeralStorage="1Gi"，仍返回 1001000。
- 第 8 次：内存由 1Gi 调整为公开页面默认的 8Gi，仍返回 1001000，未证实与内存下限有关。
- 第 9 次：任务角色键由 SDK 注释示例 t0 改为页面默认 task1，仍返回 1001000，未证实与角色名有关。
- 第 10 次：完整匹配公开页面的 PoolName 缺省、PositiveTags/NegativeTags 空数组、Internet=false、顶层 Mount 和任务 MountGPFS，并去掉试验性 EphemeralStorage，仍返回 1001000。这是多变量对照，不据此作单字段归因。
- 只读资源预测：按公开前端的 Predict 请求结构，用相同 CPU/内存/GPU/配额模式查询，返回 Success、IsSufficient=true；这是使用同一认证传输层的诊断调用，非现有 CLI 命令覆盖证明，也不等于资源预留。
- 第 11 次：在第 10 次请求上仅移除顶层 RestartPolicy="Never" 与 BackoffLimit=0，创建成功并返回 JobId。公开控制台仅在开启相应重试策略时提交这两个字段；普通任务不提交它们。
- 结论：已证实上述策略参数组在本环境的差异。不能进一步声称单独 Never 或单独 BackoffLimit=0 就是根因，也不能认定它们在所有平台部署均不可用。客户端固定 schema 允许该组合，服务端错误未指出具体字段。
- 处理：本轮测试采用已成功的省略方式；任务程序仍有 alarm 限时，并由测试执行者观察和清理。CLI 不静默删除用户请求中的策略字段，不擅自把 Never 改成可能重复执行的策略。
- 客户端修复：特定 CreateJob 错误且请求包含这组策略字段时附加谨慎 hints，保留原 message/code/request_id/outcome_unknown，不改写请求、不重试。此为诊断体验修复，不能写成服务端兼容问题已消失。
- 资源核验：前十次拒绝均无 JobId、outcome_unknown=false；在第四次和第十次后以 Self 和本轮唯一名称前缀实时查询，均无匹配任务。之后创建的生产/验证任务已完成闭环，最终按两个精确 ID 查询均返回资源不存在，精确 ID 列表 Total=0。
- 公开控制台核对：当前页面明确将内存格式化为 `N Gi`（实际字符串无空格，例如 `1Gi`），配额模式发送 GPU="0"；因此不能无证据地将内存单位改为裸数字。控制台在私有资源组模式还会设置 UsePrivateMachine=true；单独补充该字段未解决问题。
- 挂载待验证：控制台生成的是 TaskSpec.MountGPFS 以及顶层 Mount 字符串；结构化 MountGpfsVolumes 是否可以直接用于创建，需以真实任务验证，暂不认定两种方式等价。
- 证据：各版完整请求、变更字段、请求摘要、平台 request_id 和资源核验结果均在本轮私有 summary.json 中保留，后续尝试不得覆盖前面的失败记录。

## LIVE-04：CPU Job 省略 GPU 字段与线上行为不一致

- 状态：默认 GPU 修复已通过独立验证；配合显式调度参数的新版有界快捷入口也已完成运行闭环，见 LIVE-07。不推断所有默认调度组合均可运行。
- 证据：LIVE-02 第三、四次对照中，省略 GPU 时错误为 code=100、`任务资源参数错误`，恢复 GPU="0" 后进入 code=1001000 的另一层校验。公开控制台在配额模式固定发送 GPU="0"。
- 影响与处理：原快捷创建在未传 `--gpu` 时省略该字段，本地 schema 也允许省略；现仅 Job 快捷配额模式默认补 GPU="0"，显式 GPU、SKU、Workspace 不改变。请求文件仍需按预期明确填写；对应 code=100 的缺省 GPU 错误附谨慎提示，不静默改写文件。
- 首次独立真实复测：不传 `--gpu` 的快捷命令 dry-run 含 GPU="0"，创建成功并返回 JobId；该任务随后持续 Inqueue，未验证运行和日志，已停止、删除并按 ID 与列表确认不存在。后续带显式调度参数的成功复测记录在 LIVE-07。
- 限制：尚未在其余已成功参数完全相同的条件下重新单独测试 GPU 缺省，不把错误码变化直接等同于完整根因。

## LIVE-06：停止与删除具有短暂状态传播延迟

## LIVE-07：快捷创建缺少显式调度选项与任务级时限

- 状态：客户端表达能力已补齐，新的有界快捷真实闭环通过；原排队任务也已清理，调度具体单因未确认。
- 现象：修复 GPU 默认值后的快捷命令成功提交，但观察期间任务持续 Inqueue，副本 Starting、NodeName 为空，TaskStatusCounts 中 Pending=1，没有 Running/日志/自然完成证据。
- 实际配置：该请求未提交 Qos、Priority、UsePrivateMachine；后台返回 Qos 为空、Priority=9。之前文件模式成功请求显式设置 Qos=Guaranteed、Priority="5"、UsePrivateMachine=true。存在多项差异，不能断言其中某个字段是唯一排队原因。
- 时限问题：测试进程内 alarm 只在容器实际启动后生效，不能限制排队；快捷命令此前无法传 TaskSpec.MaxWaitDuration/MaxRunningDuration。工具调用期间还出现较长时间间隔，进一步说明不能用本地轮询节奏代替服务端任务时限。
- 处理：新增 --use-private-machine/--no-use-private-machine、--qos、--priority、--max-wait-duration、--max-running-duration。默认均不注入；Priority 1–9 转为 API 字符串；时限接受正整数 s/m/h/d 并转为秒，写入 TaskSpec。显式 false 保留，与文件模式互斥，Workspace 不暴露无效选项。
- 独立复测：使用显式私有资源模式、Guaranteed、优先级 5、两项 120s 时限和原 CPU 规格，未传 --gpu，真实任务创建后进入 Running，wait 返回 Succeeded，日志确认 sum=17、GPU 请求数为 0。该次从创建到最终清理约 32 秒；没有挂载用户存储。
- 边界：这证明新入口可以表达并运行该组已验证配置，不证明先前排队由某个单独字段导致，也不把这组参数设置为全局默认。
- 两个服务端时限已被创建接口接受，但本次任务在限时前正常完成，未刻意触发平台超时终止；不能把参数接受等同于超时执行机制已验证。
- 清理证据：StopJob 成功，Delete 返回 Failed=[]，最终按 ID code=105 不存在、精确 ID 列表 Total=0；没有保留排队中的测试资源。

## LIVE-03：固定目录与当前线上平台存在差异

- 状态：已发现，未更新 SDK 基准，不据此声称完整覆盖线上功能。
- 线上文件集列表返回了 FsCluster=gpfs2/gpfs3，而部分固定目录请求的 FsCluster 枚举仅含 gpfs1。挂载 Source 是普通字符串，不受该枚举限制；需要显式 FsCluster 的命令可能被本地校验阻止。
- 当前公开控制台 JavaScript 使用 CloneJob、Predict、PredictInqueueCheck、GetAuthority、GetJobTerminal 等不在固定 Job 目录内的路由，并出现 RootfsSource 等额外字段。此为前端路由/字段证据，尚未逐个确认其公开 API 合同、认证方式或运行可用性。
- 影响：先前“215 个官方目录接口、其中 213 个已有实现”的结论限定于当时文档导航；不能扩展为当前平台所有功能仅差两个接口。
- 后续：更新固定 SDK 基准或针对有正式合同的差异维护可审计兼容层，不能仅因前端出现字段就静默修改生成目录或绕过校验。

## CLI-06：日志跟随空批次推进起点，可能漏掉迟到日志

- 状态：已修复并添加确定性离线回归；新版日志跟随已在真实验证任务上读到标记，中断退出码为 130。
- 现场症状：生产任务已进入 Running 并写出产物；早期 `logs --follow` 运行约 12 秒后中断无输出，稍后单次历史查询可读到生产标记。单凭该现象不能排除日志索引延迟等其他因素。
- 确定性复现：第一轮查询返回空列表；第二轮索引才出现一条较早时间戳的日志。旧代码在空批次后将 Start 推到 End 减 3 秒，第二轮范围已经排除了这条迟到日志。
- 处理：没有观察到有效事件时间戳时保留查询起点，不把空结果当成已消费的时间边界。
- 证据区分：真实新版 follow 验证的是已入库日志读取与中断行为；可控“先空响应、再迟到旧事件”的边界由离线回归验证，未声称在真实平台人为重现了固定索引延迟。
- 限制：这项修复不承诺高吞吐、乱序日志的严格恰好一次投递；有上限的日志窗口及已有时间边界去重仍有原有适用范围。
