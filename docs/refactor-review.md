## 架构检查

- `cli.py` 只保留全局选项和命令装配，命令按域迁移到 `commands/`。
- 创建请求的资源组合规则移到 `creation.py`；分页、解析、等待与日志规则继续复用 `workflows.py`。
- 客户端编排、协议与传输分别落在 `client.py`、`protocol.py`、`transport.py`。
- 对核心模块执行 AST 导入检查，未发现直接依赖 Click 或 CLI 适配层。检查范围是静态导入，不代表任意动态导入的隔离证明。
- 架构文档明确：响应解析包含下载文件 I/O，完整响应先进入内存，尚未提供流式下载。

## 发现与修复

| 级别 | 触发与影响 | 修复位置 | 回验 |
|---|---|---|---|
| P1 | HTTP 200 的业务错误和 JSON 下载错误若回显当前凭据/签名，Python 异常原本可能泄露秘密；CLI 的末端脱敏无法保护脚本调用者 | `client.py` 收集已知秘密，`protocol.py` 统一处理错误消息 | 两类合成错误均只含脱敏标记，保留业务码与请求 ID，失败下载保留原文件 |
| P2 | 写请求收到 JSON 数组等非对象响应，原实现报错却未标记执行结果未知，可能诱使调用者重复提交 | `protocol.py` 的非对象响应分支 | 分别验证读请求为已知失败、写请求为结果未知 |

两项是离线复现的错误处理缺口；没有声称真实平台已经触发这些情况。
